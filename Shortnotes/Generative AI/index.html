Text → math, done right

LangChain embeddings reference

The step right after splitting: turning each chunk into a dense vector that captures meaning, not just keywords. Foundations, every major provider, constructor arguments and production tips — no vector database content here, just the embedding layer itself.

Foundations

Em

What is an embedding?

A fixed-length vector of floating-point numbers representing the meaning of text in high-dimensional space. Texts with similar meaning land close together geometrically, regardless of exact wording — this is what lets "car" and "automobile" match even with zero shared keywords.

"king" → [0.021, -0.443, 0.117, ..., 0.089]   # e.g. 1536 numbers
Ds

Dense vs sparse vs hybrid

TypeRepresentationExampleStrength
SparseMostly zerosTF-IDF, BM25Exact keyword matching
DenseCompact, every dim meaningfulOpenAI, Gemini, BGESemantic matching
HybridWeighted fusion of bothBM25 + dense rerankBest of both — common in enterprise
Co

Cosine similarity

The default distance metric for text embeddings — measures the angle between two vectors, ignoring magnitude. Range −1 (opposite) to 1 (identical direction).

cosine_similarity(A, B) = (A · B) / (‖A‖ × ‖B‖)

import numpy as np
def cosine_similarity(a, b):
    a, b = np.array(a), np.array(b)
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))
Dp

Dot product & Euclidean distance

If vectors are normalized (unit length), dot product ranks identically to cosine similarity — why many vector DBs default to it internally, it skips the division. Euclidean distance measures straight-line distance instead of angle; sensitive to magnitude, so less common for text unless pre-normalized.

dot_product(A, B)  = Σ(Aᵢ × Bᵢ)
euclidean(A, B)     = √Σ(Aᵢ - Bᵢ)²
Dm

Dimensions

Dimension count = length of the output vector. Higher dimensions capture more nuance but cost more storage/compute per comparison. Many modern models support Matryoshka Representation Learning (MRL) — truncating to fewer dimensions via a dimensions argument while preserving most of the quality.

ModelDimensions
Nr

Normalization

Normalizing vectors to unit length (‖v‖ = 1) makes dot product equivalent to cosine similarity — many vector DBs assume normalized vectors for their fastest index types. Most provider SDKs (OpenAI, Gemini) already return normalized vectors by default — verify before double-normalizing.

import numpy as np
def normalize(vec):
    v = np.array(vec)
    return (v / np.linalg.norm(v)).tolist()

Production notes

Query vs document embeddings

Providers like Gemini, Cohere, BGE and E5 differentiate embedding queries from embedding documents, via a task_type/input_type param or a text prefix. Using the same call for both works, but underperforms the provider's intended asymmetric retrieval setup.

query_vec = query_embedder.embed_query(user_question)
doc_vecs  = doc_embedder.embed_documents(chunk_texts)

Batch, don't loop

Always batch instead of looping embed_query per chunk — batching cuts API round-trips dramatically (10x+ throughput on large corpora). Cache embeddings for unchanged content to avoid re-embedding on every ingestion run.

texts = [doc.page_content for doc in chunks]
vectors = embeddings.embed_documents(texts)

Never mix models

Pin exact model versions in production — embedding a new corpus with a different model version than your existing index causes silent quality degradation. Vectors from two different models are never directly comparable, even at the same dimension count.

Foundations

Vd

Why a vector database?

A plain Python list of vectors works for a few thousand documents. Beyond that, linear scan becomes too slow, and you lose native persistence, filtering, concurrent access, CRUD, sharding, and replication. A vector database stores embeddings alongside source text and metadata, purpose-built to find the closest stored vectors to a query vector — at scale, across millions to billions of entries.

The retrieval layer

Retriever — the universal interface

Every vector store converts to a standard Retriever interface — this is what you actually plug into a chain. search_type can be "similarity" (standard top-k), "mmr" (diversity-aware, avoids redundant near-duplicates), or "similarity_score_threshold" (only above a minimum score).

retriever = db.as_retriever(
    search_type="similarity",       # or "mmr", "similarity_score_threshold"
    search_kwargs={"k": 4}
)
relevant_docs = retriever.invoke("What is FluenzyAI's tech stack?")

Metadata filtering

Scope semantic search to a subset — filter syntax varies slightly per DB (Chroma dict filters, Qdrant payload filters, Pinecone metadata filters); always check the specific DB's operator support ($eq, $in, $gte).

results = db.similarity_search(
    "interview preparation tips",
    k=5,
    filter={"doc_type": "blog", "language": "en"}
)

Hybrid search

Combines dense (semantic) + sparse (keyword/BM25) scoring — catches both meaning matches and exact term matches (product codes, names) that pure semantic search can miss.

from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever

bm25_retriever = BM25Retriever.from_documents(final_documents)
bm25_retriever.k = 5
vector_retriever = db.as_retriever(search_kwargs={"k": 5})

hybrid_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.4, 0.6],
)

Reranking

A first-pass retriever fetches a broad candidate set (e.g. top 20), then a reranker model re-scores them for precision, returning a smaller top-k (e.g. 5) — improves precision even when the base retriever already looks relevant.

from langchain.retrievers import ContextualCompressionRetriever
from langchain_cohere import CohereRerank

compressor = CohereRerank(model="rerank-english-v3.0", top_n=5)
reranking_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=db.as_retriever(search_kwargs={"k": 20}),
)

Parent Document Retriever

Indexes small chunks for precise search, but returns their larger parent chunk/document for generation — balances retrieval precision with generation context.

from langchain.retrievers import ParentDocumentRetriever
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain.storage import InMemoryStore

parent_splitter = RecursiveCharacterTextSplitter(chunk_size=2000)
child_splitter = RecursiveCharacterTextSplitter(chunk_size=400)

retriever = ParentDocumentRetriever(
    vectorstore=db, docstore=InMemoryStore(),
    child_splitter=child_splitter, parent_splitter=parent_splitter,
)

Multi-vector & contextual compression

Multi-vector retrieval stores multiple representations per document (e.g. a summary vector + full chunk vector) — search the summary, return the full chunk. Contextual compression strips irrelevant sentences out of each retrieved chunk before sending to the LLM, cutting noise and token cost.

answer = llm.invoke(f"Context:\n{context}\n\nQuestion: What are the candidate's key skills?")

Scaling & enterprise best practices

Enterprise best practices

  1. Match your DB choice to existing infra first (pgvector on Postgres, MongoDB Atlas on Mongo) before adding a new system.
  2. Always version your collection alongside the embedding model — never mix vectors from two different models in one collection.
  3. Use metadata filtering to scope multi-tenant or multi-source data rather than creating excessive tiny collections.
  4. Start with similarity_search; add MMR/hybrid/reranking only once you observe a real precision problem — extra retrieval stages cost latency and money.
  5. Load-test retrieval latency and recall at production-scale vector counts — behavior at 1k vectors doesn't predict behavior at 1M.
  6. Back up vector data separately from your primary DB if it isn't already durable — some ANN indexes are expensive to rebuild.

RAG fundamentals

The concept, the problems it actually solves, and where it stops being the right tool.

Wr

What is RAG?

Retrieval-Augmented Generation looks up relevant information from an external knowledge source at query time and inserts it into the LLM's prompt before generation — instead of relying only on what the model memorized during training. The LLM's parameters stay frozen; only the context window changes per request.

Wy

Why RAG exists

Two failure modes it targets directly: knowledge cutoff (the model has never seen your private data or anything after training) and hallucination on unknown facts (a model asked about something it doesn't know tends to guess fluently rather than say "I don't know"). Grounding generation in retrieved text gives the model something real to cite instead of guessing.

Lc

The RAG lifecycle

When to use RAG

  • Answers must cite private, proprietary, or frequently-changing data
  • You need traceable sources, not just an answer
  • The knowledge base is larger than any context window can hold
  • Data changes often enough that retraining isn't practical

When NOT to use RAG

  • The task needs a new skill or style, not new facts — that's fine-tuning
  • The whole corpus fits comfortably in the model's context window and cost isn't a concern — try long-context first
  • The task is closed-book reasoning/creativity with no external facts needed
  • Sub-100ms latency is required and retrieval's round-trip won't fit

RAG's own limitations

RAG reduces hallucination, it doesn't eliminate it — a model can still misread correctly-retrieved context or blend it with memorized facts. Retrieval quality is a hard ceiling: perfect generation on top of the wrong chunks still produces a wrong, confidently-stated answer. Garbage in, fluent garbage out.

Basic (Naive) RAG

Query → embed → similarity search → top-k → concatenate → prompt → generate. No rewriting, no reranking, no compression. The starting point every advanced technique below improves on.

Request flow

AspectBasic RAG
StrengthSimple, cheap, fast to ship, easy to debug
WeaknessBrittle on vague/ambiguous/multi-part questions; no correction if retrieval misses
Production suitabilityPrototypes, low-stakes internal tools, narrow single-topic corpora

Complete example — PyPDFLoader → RecursiveCharacterTextSplitter → Embeddings → FAISS

from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import FAISS
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate

# 1. Load
docs = PyPDFLoader("handbook.pdf").load()

# 2. Split
splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=120)
chunks = splitter.split_documents(docs)

# 3. Embed + store
embeddings = OpenAIEmbeddings(model="text-embedding-3-large")
db = FAISS.from_documents(chunks, embeddings)
retriever = db.as_retriever(search_kwargs={"k": 4})

# 4. Prompt + generate
prompt = ChatPromptTemplate.from_template(
    "Answer only from the context below. If the answer isn't there, say so.\n\n"
    "Context:\n{context}\n\nQuestion: {question}"
)
llm = ChatAnthropic(model="claude-sonnet-5")

def answer(question):
    docs = retriever.invoke(question)
    context = "\n\n".join(d.page_content for d in docs)
    return llm.invoke(prompt.format(context=context, question=question))

Query transformation

The user's literal wording is frequently the worst possible search query — short, ambiguous, or missing terms your documents actually use. This stage rewrites, expands or splits the query before it ever touches the retriever.

Query routing & classification

Before retrieving anything, classify the query's intent (factual lookup vs. summarization vs. small talk) and route it to the right retriever, tool, or a "no retrieval needed" fast path — cuts latency/cost on queries that never needed retrieval at all.

Conversational query rewriting

In multi-turn chat, "what about the second one?" is unsearchable on its own. Rewrite it into a standalone query using chat history before retrieval — the single highest-leverage fix for chat-based RAG.

from langchain.chains import create_history_aware_retriever
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

rewrite_prompt = ChatPromptTemplate.from_messages([
    MessagesPlaceholder("chat_history"),
    ("human", "{input}"),
    ("human", "Given the above conversation, rewrite the last question "
               "as a standalone question searchable without chat history."),
])
history_aware_retriever = create_history_aware_retriever(llm, retriever, rewrite_prompt)

Context engineering

Retrieval gets you candidate chunks. What actually reaches the LLM — how they're filtered, ordered and trimmed — decides whether the model uses them well or drowns in noise.

The "lost in the middle" problem

LLMs attend most reliably to the start and end of a long context and lose precision on facts buried in the middle. Put your highest-confidence chunk first and last, and keep the least relevant retrieved chunks (if included at all) in the middle.

Token budgeting

Fix a hard token ceiling for retrieved context (leaving room for system prompt, chat history and the answer itself) and truncate/drop lowest-scored chunks to fit — never let retrieval silently blow the context window.

import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o")

def fit_to_budget(docs, max_tokens=3000):
    out, used = [], 0
    for d in docs:  # docs pre-sorted by relevance score, descending
        n = len(enc.encode(d.page_content))
        if used + n > max_tokens:
            break
        out.append(d); used += n
    return out

Deduplication & citation construction

Near-duplicate chunks (common with overlapping splits) waste tokens without adding information — dedupe by source id or embedding similarity before assembly. Attach a stable source/chunk_id to every chunk's metadata so the final answer can cite exactly which passage it used.

Grounded, citation-aware generation

Instruct the model to answer only from supplied context and to cite the source id/number for every claim — this alone materially reduces confident fabrication and makes hallucinations auditable when they happen.

SYSTEM_PROMPT = """Answer strictly using the numbered sources below.
Cite the source number in brackets after every claim, e.g. [2].
If the sources don't contain the answer, say "I don't have enough information" —
do not use outside knowledge."""

Abstention — teaching "I don't know"

Explicitly permitting (and rewarding, in eval) an "insufficient information" response is what actually suppresses hallucination — a model only ever prompted to answer will always produce an answer, right or not.

GraphRAG

Vector search finds semantically similar chunks but is blind to explicit relationships ("who reports to whom", "which component depends on which"). GraphRAG extracts entities and relationships into a knowledge graph and retrieves via traversal, alone or fused with vector search.

When GraphRAG beats standard RAG

  • Multi-hop questions ("who worked with the person who led project X?")
  • Domains with dense, explicit relationships — org charts, supply chains, codebases, legal case citations
  • Global/aggregate questions across the whole corpus, not one document ("summarize all risks mentioned anywhere")

Agentic RAG

Instead of one fixed retrieve-then-generate pass, an agent decides whether to retrieve, what to search for, evaluates what came back, and can retrieve again — trading latency and cost for resilience on hard, multi-step questions.

Retriever-as-tool with LangGraph

from langgraph.prebuilt import create_react_agent
from langchain_core.tools import create_retriever_tool

retriever_tool = create_retriever_tool(
    retriever, "search_knowledge_base",
    "Search the internal knowledge base for facts needed to answer the question."
)
agent = create_react_agent(llm, tools=[retriever_tool])
result = agent.invoke({"messages": [("human", "Compare Q1 and Q3 churn drivers")]})

Production considerations

  • Cap retrieval loop iterations — unbounded agents can loop until a timeout or budget is exhausted
  • Log every tool call and its result for observability; agent failures are hard to debug blind
  • Restrict tool permissions (read-only retrieval by default) to bound the blast radius of a bad plan
  • Latency and cost scale with steps taken — reserve for questions basic/advanced RAG genuinely can't answer

Multimodal RAG

Real documents aren't pure text — tables, charts, scanned pages and images carry information that text-only chunking throws away. Multimodal RAG extracts and indexes each modality so retrieval can surface the right image or table, not just nearby prose.

Summary-indexed multi-vector pattern

The dominant practical approach: use a vision-capable LLM to generate a text summary of each image/table, embed and index the summary, but return the original image/table (linked via a doc store) once it's retrieved — search quality of text, generation quality of the original artifact.

from langchain.retrievers.multi_vector import MultiVectorRetriever
from langchain.storage import InMemoryStore
import base64

def summarize_image(image_path, vision_llm):
    with open(image_path, "rb") as f:
        b64 = base64.b64encode(f.read()).decode()
    return vision_llm.invoke([
        {"role": "user", "content": [
            {"type": "text", "text": "Describe this chart/table for search retrieval."},
            {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{b64}"}},
        ]}
    ]).content

# summary -> embedded + indexed; original image bytes -> docstore, linked by id
retriever = MultiVectorRetriever(vectorstore=db, docstore=InMemoryStore(), id_key="doc_id")

RAG security

Retrieval pulls untrusted content directly into the model's context — that's a real attack surface. Defensive engineering, not exploitation detail.

Indirect prompt injection via documents

A retrieved document can contain text instructing the model to ignore its system prompt or take an unintended action. Mitigate by clearly delimiting retrieved content as untrusted data (never as instructions) in the prompt template, and never letting retrieved text alone trigger tool calls.

Cross-tenant data leakage

Enforce tenant/user access scope as a hard metadata filter at the retriever level — not as a prompt instruction, which a crafted query or injected document can override. Test retrieval isolation the same way you'd test any access-control boundary.

Document-level permissions

Real-world corpora mix documents with different access levels. Carry the source system's permission model into chunk metadata so retrieval never surfaces a chunk the requesting user isn't authorized to see, rather than filtering after the fact.

Retrieval & citation poisoning

A malicious or low-quality document injected into the corpus can get retrieved and cited as if authoritative. Validate/sanitize ingestion sources, weight trusted sources higher, and treat public/user-submitted content as lower-trust than curated internal docs.

Fundamentals

    
A prompt is the only interface you have to a model's behavior — no retraining, no new weights, just the words you send it. Getting reliable behavior out of that interface is the whole discipline.

    

      

        
Wp
What is prompt engineering?

        
The practice of designing the input text (instructions, context, examples, format constraints) that shapes a model's output — deliberately, testably, and repeatably, rather than by trial and error alone.

      

      

        
Vs
Prompt vs. instruction vs. system message vs. context

        

          
            
PromptThe full text sent to the model — everything below combined

            
InstructionThe specific task directive ("summarize this", "classify this")

            
System messageStanding behavior set once per conversation, higher priority than user turns

            
ContextSupporting information the model needs but didn't generate itself (retrieved docs, history, user data)

          
        

      

      

        
Deterministic vs. probabilistic behavior

        
LLM output is sampled, not computed — the same prompt can legally produce different valid completions. temperature controls how much: near 0 for consistent/extractive tasks, higher for creative variation. top_p caps the sampling pool by cumulative probability instead of a flat temperature scale — the two are usually tuned one at a time, not both aggressively.

      

      

        
Context windows & token budgeting

        
Every model has a hard token ceiling covering system + history + context + input + reserved output space. Budget it explicitly — an unbudgeted prompt that silently exceeds the window either truncates unpredictably or errors outright.

      

      

        
Hallucination & grounding

        
Asked something it doesn't know, a model tends to produce a fluent, confident guess rather than admit uncertainty. Grounding — supplying real source text and instructing the model to stick to it — is the main prompt-level lever against this; see RAG Prompting below.

      

      

        
Instruction hierarchy

        
Well-behaved models weight system instructions above developer instructions above user turns above untrusted retrieved/tool content. Design prompts assuming a user (or a document) may try to override your system instructions — never rely on the model "just knowing" what's authoritative without saying so explicitly.

Why schemas beat prose instructions

        
A schema is checked by the API/parser, not just "requested" — malformed output is rejected or retried mechanically instead of silently shipped. It also survives model swaps better: the same schema works across providers that support structured outputs, while prose formatting instructions drift in how literally each model follows them.

Context engineering vs. prompt engineering

    
Prompt engineering shapes the instructions; context engineering shapes what information those instructions have to work with. The full treatment — token budgeting, lost-in-the-middle, compression, deduplication — already lives in the RAG Pipelines module; this is the short version.

    

      

        
The distinction

        
Prompt engineering asks "how do I phrase this instruction?" Context engineering asks "what information does the model actually need to see, in what order, within what budget?" A perfectly phrased prompt over irrelevant or overflowing context still fails.

      

      

        
Conversation history & memory

        
Don't replay full history forever — summarize or window older turns, and keep only the memory/user-profile facts actually relevant to the current turn. Unbounded history is the most common silent token-budget killer in production chat apps.

      

    

    
Related

  


  
  

    
Reasoning & structured problem solving

    
Modern practice favors observable, structured reasoning outputs and external verification over asking a model to expose its raw internal chain-of-thought — that hidden reasoning isn't meant to be requested or relied upon by applications.

    

      

        
Problem decomposition

        
Break a complex ask into explicit, independently-answerable sub-steps the model fills in one at a time or in a structured list — easier to verify and to fix piecemeal than one monolithic answer.

      

      

        
Intermediate structured outputs

        
Ask for a visible intermediate artifact — a plan, a list of extracted facts, a draft — before the final answer. Structured and checkable, unlike free-form hidden reasoning.

      

      

        
Critique-and-revise

        
Generate a draft, then a second pass explicitly checks it against the original constraints and produces a revision — catches constraint violations a single pass misses.

      

      

        
Programmatic / external validation

        
Where possible, verify outputs with actual code — a JSON schema validator, a SQL EXPLAIN, a unit test — instead of asking the model to self-certify correctness. External verification catches errors self-review can't see.

Routing implementation

      

        
ROUTES = {
    "code": "You are a senior software engineer. Answer with working code and a brief explanation.",
    "data": "You are a data analyst. Answer with a clear methodology and, where relevant, SQL or pandas.",
    "general": "You are a helpful, concise assistant.",
}

def route(user_message: str) -> str:
    intent = llm.invoke(
        f"Classify this request as exactly one of code, data, general. Reply with one word.\\n\\n{user_message}"
    ).content.strip().lower()
    system_prompt = ROUTES.get(intent, ROUTES["general"])
    return llm.invoke([{"role": "system", "content": system_prompt}, {"role": "user", "content": user_message}]).content

        
      

    

  


  
  

    
Tool / function calling prompts

    
The tool's name, description and parameter schema are the prompt for when and how the model uses it — vague tool descriptions are the most common cause of a model never calling (or wrongly calling) a tool.

    

      
Well-specified tool definition

      

        
tools = [{
    "type": "function",
    "function": {
        "name": "get_order_status",
        "description": (
            "Look up the current shipping status of a customer order. "
            "Call this whenever the user asks where an order is, whether it shipped, "
            "or for a tracking number. Do not guess a status without calling this."
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "order_id": {"type": "string", "description": "The order ID, e.g. 'ORD-48213'."},
            },
            "required": ["order_id"],
        },
    },
}]

        
      

      
Notice the description tells the model when to call it, not just what it does — "call this whenever..." — and explicitly forbids guessing instead. Both materially change how reliably the model reaches for the tool.

Prompt security

    
Defensive engineering — not exploitation detail.

    

      

        
Prompt injection & jailbreak attempts

        
Treat every instruction embedded in user input or retrieved/tool content as untrusted — never let it override the system prompt's rules. Clearly delimit untrusted content and state explicitly that instructions inside it are not to be followed.

      

      

        
System prompt exposure

        
Explicitly instruct the model not to reveal its system prompt or internal tool schemas, and don't rely on that instruction alone for anything genuinely sensitive — nothing sent to the model is guaranteed unextractable.

      

      

        
Cross-user / cross-tenant leakage

        
Never assume a prompt-level instruction ("only discuss this user's data") is a security boundary — enforce tenant/user scoping at the data-access layer, the same as any other authorization concern.

      

      

        
Sensitive information leakage

        
Don't put secrets, internal credentials or unnecessary PII in a prompt at all — anything in context can, in principle, be surfaced back out through some phrasing of a request.

      Connecting models to the real world
      
  
      Tool Calling & MCP
      
  
      Structured interfaces that let a model act on real systems — from a single function-calling schema up to a governed, multi-server MCP deployment. Covers the evolution: prompt → structured output → function calling → tool calling → tool registry → MCP → external systems.
      
  
      MCP terminology below reflects the 2026-07-28 specification revision (stateless protocol core; two standard transports, stdio and Streamable HTTP — the older HTTP+SSE transport and the initialize-handshake session model are deprecated with a year-long offramp). Many servers in production today still run the earlier session-based model — both are covered where it matters.
      

  
      
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
    
  
      

  
  
      
    
      Fundamentals
      
    
      A tool is a named, schema-described action a model can request — the model never executes anything itself; it emits a structured request, and your infrastructure decides whether and how to run it.
      
    
      
    
      
      
      
        
      Wt
      What is a tool?
      
        
      A function the model can choose to invoke, described to it as a name, a description, and a JSON Schema of arguments. The model outputs a structured call (never runs code itself); your application validates, authorizes and executes it, then returns the result for the model to use in its next turn.
      
      
      
      
      
        
      Wy
      Why LLMs need tools
      
        
      A model's knowledge is frozen at training time and it can't take real actions on its own — tools give it live data (via read tools) and real-world effect (via write tools), turning a text generator into something that can actually look things up and get things done.
      
      
      
      
      
        
      The evolution
      
        
      
      
      
    
      
    
      Related

      Function calling
      
    
      The mechanism underneath every tool call — a JSON Schema describing what the model may request.
      
    
      
      
      Annotated example
      
      
      
        
      {
  "name": "get_weather",
  "description": "Get current weather for a location. Call this whenever the user asks about weather.",
  "parameters": {
    "type": "object",
    "properties": {
      "location": { "type": "string", "description": "City and country, e.g. 'Lyon, France'." },
      "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["location"]
  }
}
      
        
      
      
      
      
        
          
      nameUnique, machine-readable identifier the model uses to request this tool — short, verb-first, no ambiguity with other tools.
      
          
      descriptionThe actual prompt for when to call this tool, not just what it does — the single highest-leverage field for reliable invocation.
      
          
      parameters (JSON Schema)The argument shape — types, enums, required vs. optional. A stricter schema means fewer malformed calls to handle downstream.
      
          
      requiredArguments the model must supply — anything omitted here the model may (and will) leave out.
      
              
      
      
    
      
  
      

  
  
      
    
      Tool schema design
      
    
      Small, precise tools are easier for the model to select correctly and easier for you to secure — a "do everything" tool is neither.
      
    
      
      
      
        
      Bad vs. good granularity
      
        
      
          
            
      Baddo_everything(action, data) — one tool, ambiguous action string, unbounded data shape
      
            
      Goodsearch_customer(), get_order(), create_ticket(), cancel_order() — each with a narrow, typed, single-purpose schema
      
                
        
      
        
      A narrow tool has one clear permission level, one clear failure mode, and one clear description to get right — a mega-tool inherits the union of every risk and every ambiguity of everything it can do.
      
      
      
      
      
        
      Design checklist
      
        
        
          
      • Clear, unambiguous name and a description that states when to call it
        • 
          
      • Minimal parameters — every optional field is another way to get it wrong
        • 
          
      • Strong types and enums over free-text where the value set is known
        • 
          
      • A defined output schema, not just a defined input schema
        • 
          
      • A defined error shape, so failures are structured, not free text
        • 
          
      • Explicit idempotency — is calling it twice with the same args safe?
        • 
          
      • Explicit side effects — documented, not left to be discovered in production
        • 
        
      
      
      
    
      
  
      

  
  
      
    
      Tool registry
      
    
      A central catalog of every tool available to your models/agents — not just a list, but the source of truth for what each tool needs to run safely.
      
    
      
    
      
      
      Registry entry fields
      
      
      
        
          
      id / versionStable identifier and semantic version — tools are versioned APIs, not static text
      
          
      inputSchema / outputSchemaWhat goes in, what comes back — both enforced, not just documented
      
          
      permissionsWho/what may invoke it (see Permissions below)
      
          
      timeout / retryPolicyHow long to wait, how (and whether) to retry on failure
      
          
      sideEffectsnone / read / write / destructive — drives approval and logging requirements
      
          
      authentication / owner / statusHow the tool authenticates to its backend, who owns it, and whether it's active/deprecated
      
              
      
      
    
      
  
      

  
  
      
    
      Tool execution pipeline
      
    
      Every stage between "the model asked for this" and "the model sees a result" is a place to catch a bad call before it does damage.
      
    
      
  
      

  
  
      
    
      Tool permissions
      
    
      The prompt is not a security boundary. A system instruction saying "never delete customer records" is a request the model usually honors — it is not enforcement. Permissions belong in trusted infrastructure outside the model's control.
      
    
      
      
      
        
      ToolClass
      
        
          
      search_databaseRead-only
      
          
      create_ticketWrite
      
          
      delete_customerDestructive
      
          
      production_deployPrivileged
      
              
      
      
    
      
    
      Enforce with allowlists/denylists and scope (user / admin / service / tenant) checked server-side on every call — never inferred from the conversation.
      
  
      

  
  
      
    
      Tool routing
      
    
      Beyond letting the model pick freely from every tool, routing narrows the candidate set first — by intent, capability, permission, cost or latency — before the model ever sees the list.
      
    
      
  
      

  
  
      
    
      Tool errors & retry policy
      
    
      
    
      
      
      
        
      Error classes
      
        
        
          
      • Invalid arguments — reject before execution, return a structured error the model can act on
        • 
          
      • Auth/authorization failures — never retry silently; surface clearly
        • 
          
      • Timeout / rate limit / network failure — usually retryable, with backoff
        • 
          
      • Partial / dependency failure — decide per-tool whether a partial result is usable
        • 
        
      
      
      
      
      
        
      Example retry configuration
      
        
      
          
      {
  "maxRetries": 3,
  "retryableErrors": ["timeout", "rate_limit", "network"],
  "backoff": "exponential",
  "baseDelayMs": 200,
  "jitter": true,
  "circuitBreaker": { "failureThreshold": 5, "resetAfterMs": 30000 }
}
      
          
        
      
        
      An example configuration, not a universal recommendation — tune per tool. Never retry non-idempotent destructive calls without an idempotency key.
      
      
      
    
      
  
      
  
  
      
    
      MCP fundamentals
      
    
      The Model Context Protocol standardizes how AI applications discover and use tools, resources and prompts from external servers — one protocol instead of a bespoke integration per system.
      
    
      
      
      
        
      The problem it solves
      
        
      Without a shared protocol, every AI application needs custom integration code for every tool source it connects to — an M×N problem (M applications × N systems). MCP standardizes the interface so any compliant host can talk to any compliant server.
      
      
      
      
      
        
      Core roles
      
        
      
      
      
    
      
  
      

  
  
      
    
      MCP architecture
      
    
      Click a component to jump to its section below.
      
    
      
  
      

  
  
      
    
      Host, client & server
      
    
      
      
      
        
      Host
      
        
      The AI application itself (an IDE, a chat app, an agent runtime). Owns user interaction, manages one or more clients, and enforces the outer permission/security boundary — a host typically runs one client per connected server.
      
      
      
      
      
        
      Client
      
        
      Lives inside the host, maintains a 1:1 connection to one MCP server, negotiates capabilities, discovers tools/resources/prompts, and handles the request/response and error plumbing for that connection.
      
      
      
      
      
        
      Server
      
        
      Exposes tools, resources and prompts, validates and authenticates every incoming request, executes tool calls, and returns structured results — a thin, focused process per system it fronts (database, filesystem, SaaS API, etc.).

      Transports
      
        
      
          
            
      stdioNewline-delimited JSON-RPC over a local process's stdin/stdout — the common choice for locally-run servers
      
            
      Streamable HTTPA single HTTP endpoint; replies arrive as a JSON response or a request-scoped stream — the standard for remote servers
      
                
        
      
        
      The older HTTP+SSE transport is deprecated (year-long offramp from the 2026-07-28 revision) — new servers should target Streamable HTTP for remote deployments.
      
      
      
      
      
        
      Capability discovery
      
        
      
      
      
      
      
        
      Session lifecycle
      
        
      Most servers deployed today follow the earlier connection-scoped model: connect → initialize handshake → negotiate capabilities → discover → use → disconnect. The 2026-07-28 revision moves the protocol core to be stateless (no handshake-bound session); a server that needs to carry state across calls mints an explicit handle from a tool and has the model pass it back as an argument on later calls, rather than relying on hidden transport-level session state.
      
        
      
      
      
    
      
  
      

  
  
      
    
      MCP security
      
    
      The prompt is not a security boundary. Permissions, authentication and authorization must be enforced by infrastructure the model cannot talk its way around.
      
    
      
    
      
      
      
        
      ThreatAttack surfaceMitigation
      
        
      
      
    
      
  
      

  
  
      
    
      Authentication & authorization
      
    
      Authentication answers "who are you?"; authorization answers "what are you allowed to do?" — both are needed, and neither is the model's job.
      
    
      
    
      
      
      
        
      Authentication
      
        
      Identity verification for the client and, where relevant, the end user — commonly OAuth-based authorization-code flows for remote servers, or process-level trust for local stdio servers. Access tokens are validated on every request; never embedded in a prompt or stored client-side in plaintext.
      
      
      
      
      
        
      Authorization
      
        
      Scope- and role-based checks on every tool call and resource read — tenant isolation enforced at the data layer, not inferred from which tools happen to be listed. A user's token scope should bound exactly what a tool call on their behalf can touch.
      
      
      
    
      
    
      Never place secrets, tokens or credentials in frontend/client code — real integrations validate and store credentials server-side.
      
  
      

  
  
      
    
      Observability & audit logging
      
    
      
      
      
        
      What to track
      
        
      Server connections, tool calls and their latency, errors, auth/authz failures, resource access, prompt usage, request volume, retry counts — logs, metrics, traces and a distinct security-events stream.

      Redact PII and secret values before they ever reach a log line — audit what happened, not the sensitive payload itself.
      
      
      
    
      
  
      

  
  
      
    
      Reliability & versioning
      
    
      
      
      
        
      Health checks & graceful degradation
      
        
      
      
      
      
      
        
      Treat tools as versioned APIs
      
        
      Version the protocol, the server, and individual tool schemas independently. Deprecate before removing, support at least one prior schema version during migration, and never silently change a tool's argument shape under callers still targeting the old one.

        AI Observability
        
  
        Collecting and analysing the behaviour, performance, reliability, cost, security and quality of AI applications in production.
        
  
        DEMO DATA. No telemetry collector is connected. Traces below are deterministic local samples; calculators run locally; alert rules and pipelines are configuration previews and nothing is deployed or delivered.
        
  
        
    
  
        

  
        Fundamentals: logs, metrics, traces
        
    
        Monitoring detects known conditions. Observability lets you ask new questions about what happened. Evaluation tells you whether the output was good; tracing shows how it was produced. They complement each other.
